# SecurePass: security summary for the client

This page answers one question: **what stops someone from cancelling bookings or flights without a reason, and from hacking the site in general?** Each line names the automated test that proves it.

## 1. The cancellation problem

Unexplained cancellations have only a few possible causes. Each one now has a control.

| How a cancellation could happen without a reason | Control | Evidence |
|---|---|---|
| Someone logs in to a customer's account (stolen or guessed password) and cancels | A cancellation asks for the account password again, and for a code from the authenticator app when two-step login is on | test_cancel_with_wrong_password_is_refused_and_logged, test_two_factor_account_must_give_a_code |
| A stolen session is used to cancel many bookings at once | At most 3 cancellations in 10 minutes per account; the 4th is refused and an alert is logged | test_four_cancellations_in_ten_minutes_are_stopped |
| A hidden page on another site tricks a logged-in customer into cancelling | Every action needs a secret token tied to the visit; opening a link never cancels anything | test_a_get_request_never_cancels, test_booking_and_cancel_need_a_csrf_token |
| A customer cancels another customer's booking by guessing its reference | A booking can only be opened or cancelled by its owner | test_only_the_owner_can_cancel |
| A cancellation is made with a made-up or empty reason | The reason must come from a fixed list; anything else is refused | test_cancel_without_reason_is_refused, test_cancel_with_unknown_reason_is_refused |
| Nobody notices a cancellation until later | The owner is emailed at once with the network address and a "change your password" link | test_cancel_stores_reason_and_address_and_emails_the_owner |
| Staff cannot tell who cancelled or why | Every cancellation stores the reason, the time and the network address; the admin **Cancellations** page lists them and flags accounts that cancel many bookings in a day | test_admin_sees_who_cancelled_and_why, test_cancellations_page_is_for_admins_only |
| Seats are lost when a booking is cancelled twice | Cancelling twice gives the seats back only once | test_cancelling_frees_the_seats |

**How to investigate a suspicious cancellation.** Open Admin, then Cancellations. Look for the "Many today" and "No reason" marks. Note the account and the network address. Open the Security dashboard, filter the events by that account, and look for earlier failed logins. If the account was misused, unlock or reset it from the admin pages and ask the customer to turn on two-step login.

## 2. Protection against hacking in general

| Threat | Control | Evidence |
|---|---|---|
| Guessing passwords | Passwords are stored as salted hashes, must be 10 or more characters, may not be common or contain the email name; repeated failures lock the account for 15 minutes | test_common_passwords_are_refused, test_too_many_wrong_codes_lock_the_account |
| Finding which emails have accounts | Known and unknown emails get the same answer | test_known_and_unknown_emails_get_the_same_answer |
| Stolen password alone | Optional two-step login with an authenticator app; a code cannot be used twice; recovery codes are stored hashed | test_a_code_cannot_be_used_twice, test_recovery_codes_are_unique_and_hashed_with_a_key |
| Forged requests from other sites | Every form needs a CSRF token | test_admin_actions_need_a_csrf_token, test_missing_csrf_token_gets_a_friendly_400_page |
| Scripts injected into pages | A strict content security policy, escaped output and no inline scripts | test_csp_only_allows_this_site, test_event_details_are_escaped_on_the_dashboard, test_templates_work_with_the_strict_csp |
| Unsafe connections | HTTPS is forced and HSTS is sent in production; the session cookie is locked down | test_production_redirects_http_to_https, test_production_sends_hsts_over_https, test_production_session_cookie_is_locked_down |
| Normal users reaching admin pages | Every admin page checks the role on the server | test_every_admin_route_blocks_anonymous_visitors, test_every_admin_route_blocks_normal_users |
| Two people booking one seat | The database itself refuses a double-booked seat | test_the_database_itself_refuses_a_double_booked_seat |
| Brute force on sensitive actions | Rate limits on login, password change and cancellation | test_password_change_is_rate_limited |
| Losing track of what happened | Logins, bookings, cancellations, exports and denied access are written to an audit log | test_a_wrong_current_password_is_audited, test_csv_lists_bookings_and_is_audited |
| Secrets in the code | Secrets are generated by the host and never committed | test_render_blueprint_generates_the_secret_key_and_keeps_the_database_private, test_the_real_env_file_is_never_committed |
| Vulnerable libraries and code | Every change is scanned in CI (static analysis, dependency audit, CodeQL) and tested on PostgreSQL before it goes live | Manual: CI results on each pull request |
| Personal data | A user can download or delete their own data | test_export_contains_my_data_and_no_secrets, test_delete_removes_account_bookings_and_gives_seats_back |

## 3. What the client should do

1. Turn on **two-step login** for every staff and administrator account.
2. Use a long, unique password for the administrator and delete the first-install password setting from the host.
3. Look at the **Cancellations** page every day for the first weeks.
4. Keep the host's automatic database backups on and test a restore once.
5. Merge dependency updates promptly. CI tests every one before it is accepted.
6. Tell customers to use a password they use nowhere else, and to turn on two-step login.

## 4. Honest limits

- This is a demonstration system: payments are simulated and no card data is stored.
- Emails are only sent when a mail server is configured on the host.
- No system is unhackable. These controls make attacks harder, visible and traceable; a penetration test by an outside team is the right next step before real customers.
